## 1. Whole-response token budget (the "two-layer" system)

### CAP-300 — Two-layer budget ownership: `BudgetOwnership` / `ResponseBudgetPlanner` / `MaterializationPlanner`
**Status:** LIVE. **Evidence:** `src/FFOccamMcp.Core/Compile/BudgetOwnership.cs:41-77`, wired at `src/FFOccamMcp.Core/Routing/TranscodePipeline.cs:242-253` (`PrepareSurfaceBudget` → `ApplyToRequest`) and `:357-398` (`ResponseBudgetPlanner.TrimStructured`).
The public `max_tokens` on `occam_transcode` (`OccamTranscodeTool.cs:48`) is a **whole-response** budget shared across markdown + blocks + tables + chunks + media + feed + receipt. Layer 1 (`ResponseBudgetPlanner.AllocateMarkdownCap`, `ResponseBudgetPlanner.cs:85-113`) reserves a markdown floor (≥50% of pool, min 128 tokens — `MinMarkdownTokens` at `ResponseBudgetPlanner.cs:77`) and a receipt skeleton reserve (`ReceiptSkeletonTokens = 48`, `:78`), then caps structured sidecars to the remainder. Layer 2 (`MaterializationPlanner.Plan`, `MaterializationPlanner.cs:35-73`) receives only the derived **surface** cap (`Compile.BudgetOwnership.ApplyToRequest`, `BudgetOwnership.cs:66-76`) and never sees the whole-response pool — by design, per the type's own doc comment (`BudgetOwnership.cs:20-22`): "Collapsing both layers … would break byte/hash parity."
**Note:** this is real, tested architecture (own doc-comment explicitly warns against the naive merge), not vaporware — confirmed live via the two call sites above.

### CAP-301 — `ResponseBudgetPlanner.TrimStructured`: greedy prefix trim order is fixed and undocumented in `MCP_API_SPEC.md`
**Status:** LIVE. **Evidence:** `ResponseBudgetPlanner.cs:119-233`. Screenshot is dropped first (base64 dominates budget, `:139-152`), then blocks → tables → chunks → media → feed as a strict greedy prefix (`TakePrefix`, `:384-416`) — **not** by any per-bucket priority or relevance ranking. A page with `json_blocks=true, json_tables=true` and a tight `max_tokens` will silently starve tables before blocks regardless of which the caller's `focus_query` cares about more.
**Gap:** no parameter lets a caller reorder bucket priority (e.g. "prefer tables over blocks"). `MCP_API_SPEC.md`/`docs/tools-reference.md` do not document the fixed drop order — an agent cannot predict which structured field survives under a tight budget without reading this source.

### CAP-302 — `ResponseBudgetPlanner.EstimateBlock/Table/Chunk/Media/Feed`: per-item cost estimators feed both allocation and trim
**Status:** LIVE. **Evidence:** `ResponseBudgetPlanner.cs:311-383`. Each estimator sums `TokenEstimator.Estimate` over every serialized sub-field (e.g. `EstimateTable` at `:316-345` walks `Caption + SourceSelector + all headers + all cells + all Records sub-fields`). Costs are **not cached** — recomputed once in `EstimateStructuredRaw` (pre-materialization estimate, `:263-309`) and again in `TrimStructured`'s `TakePrefix` calls (post-materialization actual). This is O(n) over field text length twice per request; acceptable at current corpus sizes but worth flagging if `max_blocks`/table sizes grow.

### CAP-303 — `ResponseBudgetDiagnostics`: computed but never surfaced in any MCP response
**Status:** LIVE-INTERNAL (dead from the API-consumer's perspective). **Evidence:** built at `TranscodePipeline.cs:375-383`, stored on `TranscodeOutcome.BudgetDiagnostics` (`Routing/TranscodeOutcome.cs:55`) — but grep across `src/FFOccamMcp.Core/Tools/OccamTranscodeTool.cs` (the only consumer of `TranscodeOutcome` for response-building) shows **zero references** to `.BudgetDiagnostics`. The type's own doc comment (`ResponseBudgetDiagnostics.cs:5`) admits this: "Internal … telemetry retained for PR-F mapping and calibration." Confirmed not exposed — `OccamTranscodeCompileInfo`/`OccamTranscodeBudgetInfo` (the actually-serialized types, `OccamTranscodeModels.cs:136-144`) carry a strict subset (`Total/Markdown/Blocks/Tables/Chunks/Media/Feed/Receipt`) with no `PlannerRetries` or `SelectedAnswerUnitTokens` field.
**Gap:** an agent debugging "why did my focused answer come back incomplete" cannot see `PlannerRetries` or `SelectedAnswerUnitTokens` — only the coarser `compile.budget` byte totals and the `completeness`/`focus` semantic verdict strings (see CAP-311).

### CAP-304 — `max_tokens` client-ambient default via `occam_client_capabilities`
**Status:** LIVE, OPT-IN (declare-once). **Evidence:** `src/FFOccamMcp.Core/Client/ClientCapabilityStore.cs:70-79` (`ResolveMaxTokens`), invoked at `OccamTranscodeTool.cs:78` and `OccamDigestTool.cs:54`. Output budget = `clamp(round(context_tokens * 0.20), 512, 16384)` (`ClientCapabilityStore.cs:81-85`, `OutputFractionOfContext = 0.20`). Bootstraps from `OCCAM_CLIENT_CONTEXT_TOKENS` env var at process start (`:93-109`) or via the `occam_client_capabilities` tool call (`OccamClientCapabilitiesTool.cs`) at runtime — process-scoped singleton (`_gate`-locked), so **it is shared mutable state across concurrent tool calls in the same host process**: one client declaring `context_tokens` affects every other in-flight call's ambient default until cleared. No per-call isolation.
**Gap (concurrency correctness risk):** in a multi-session MCP host (e.g. a batch/worker pool sharing one `Program.cs` process), `Configure()` from session A silently changes the default `max_tokens` for session B's concurrent omitted-`max_tokens` calls. Not a bug in isolation (stdio transport is typically one process per client) but a real risk if `WebSocketMcpTransport` (multi-client) is in play — confirmed present in repo (`Transport/WebSocketMcpTransport.cs`, not audited in depth here — flag for CAP-connectivity subagent).

### CAP-305 — Minimum token floor enforced at the parameter layer
**Status:** LIVE. **Evidence:** `OccamTranscodeOptionsParser.TryBuild`, `Routing/OccamTranscodeOptions.cs:77-81`: `max_tokens < 128` → `invalid_arguments`. Same floor independently re-declared as `ResponseBudgetPlanner.MinMarkdownTokens = 128` (`ResponseBudgetPlanner.cs:77`) and `DigestService.MinTokenBudget = 128` (`Services/DigestService.cs:62`). Three independent literal `128`s, not a single shared constant — a future edit to one will silently desync from the others (no compile-time coupling).

## 2. Compile pipeline: selectors → fit_markdown → token budget → anchor preservation

### CAP-306 — `TranscodeCompiler.Apply`: the exact live compile order
**Status:** LIVE. **Evidence:** `src/FFOccamMcp.Core/Routing/TranscodeCompiler.cs:15-59`, called from `MaterializationPlanner.Plan` at `MaterializationPlanner.cs:40`. Fixed order: (1) `MarkdownContentFilter.ApplyWithMeta` (content_selectors scoping, `:20-25`) → (2) `FitMarkdown.Apply` (BM25 prune, `:28-31`) → (3) `TokenBudget.Apply` (hard cap, `:35-39`) → (4) `TokenBudget.PreserveDefinitionalAnchor` (re-inject a definitional paragraph the budget cut, `:40-44`). Order matters: selectors scope *before* BM25 prune sees the document, so a `content_selectors` miss short-circuits with empty text before fit_markdown ever runs (`content_selectors_miss` failure path exists at `TranscodePipeline.cs:280-299`, gated on `!planned.SelectorsMatched`).

### CAP-307 — `content_selectors`: heading-anchor scoping, not real CSS selectors
**Status:** LIVE, OPT-IN. **Evidence:** `MarkdownContentFilter.cs:81-121` (`FindSectionIndex`/`HeadingMatchesPrefix`). Despite the parameter name "selectors" and the tool description's example `["# API Reference"]` (`OccamTranscodeTool.cs:51`), this operates purely on **markdown heading text match** (prefix or substring, case-insensitive) — it has no relationship to the DOM/CSS `source_selector` strings that `json_blocks` emits (`workers/shared/lib/dom-blocks.mjs:158-197`, real CSS nth-of-type paths). Two completely different "selector" vocabularies coexist in the same tool surface under similarly-named concepts (`content_selectors` param vs. `source_selector` block field) — a plausible confusion point for an agent that tries to feed a `blocks[].source_selector` value back into `content_selectors`.

### CAP-308 — `FitMarkdown.Apply`: BM25 paragraph prune, focused vs. unfocused thresholds differ
**Status:** LIVE, OPT-IN (`fit_markdown=true`, default **true** on `occam_digest`, default **false** on `occam_transcode` — `OccamDigestTool.cs:24` vs `OccamTranscodeTool.cs:49`). **Evidence:** `Compile/FitMarkdown.cs:24-134`. Thresholds are hardcoded: `minScore = focused ? 0.06 : 0.12`, `minHeadingScore = focused ? 0.035 : 0.08` (`:43-44`) — no parameter exposes these. A 30-line boilerplate-term denylist (`BoilerplateTerms`, `:10-22`) is English-only (`"skip to main content"`, `"was this page helpful"`, `"minutes to read"`, etc.) — non-English boilerplate (cookie banners, "Поделиться", nav chrome) is not filtered by this list, though the density/link-density heuristics (`IsHighLinkDensity`, `:693-698`; `FactDensityFilter.IsLowValueBlock`) are language-agnostic via `\p{L}\p{N}` tokenization (`FocusMatcher.cs:284`, `FactDensityFilter.cs:87`).
**Gap:** `BoilerplateTerms` English-only denylist is an honesty risk on non-English pages combined with the project's own "no per-topic hardcodes" design philosophy visible everywhere else in this file (e.g. `DefinitionalConnectors` comments at `TokenBudget.cs:123-126` explicitly reject hardcoded lists) — this list is the one holdout.

### CAP-309 — `TokenBudget.Apply`: three truncation strategies, chosen by presence of `focus_query`
**Status:** LIVE. **Evidence:** `Compile/TokenBudget.cs:7-37`. `focus_window` (section-ranked truncation around the focus term, `TruncateFocusCentered`, `:39-84`) when a focus query/fragment is given and a section is found; else `sandwich` (head+tail with `<!-- SNIP: middle -->`, `:505-551`) as the **fallback** inside `focus_window` when no section wins; else `head_safe` (simple head truncation, `:485-503`) when there is no focus at all. All three insert **honesty markers** in-band (`<!-- SNIP: … -->`) so a truncated body is self-describing even without reading `compile.omitted` — a good design property, doubly redundant with CAP-310's structured manifest.
**Script-awareness:** truncation char budgets use `TokenEstimator.CharBudgetForTokens`/`FromEnd` (script-aware, `TokenEstimator.cs:67-106`), not a flat `tokens*4` — correctly avoids over-keeping CJK/Cyrillic text (see CAP-320).
**Boundary safety:** `FindSafeCutIndex` (`:553-582`) chains three post-cut adjustments — word boundary (`AdjustForWordBoundary`), markdown-link boundary (`AdjustForMarkdownLink`), and URL-in-parenthesis boundary (`AdjustForUrlParenthesis`) — each scanning up to 240 chars backward. This is real link-integrity protection (a truncation cannot land mid-`[text](url` and leave a dangling markdown link), verified by reading all three helper bodies (`:584-656`).

### CAP-310 — `OmittedManifest` / `compile.omitted`: structured "what was dropped" record
**Status:** LIVE. **Evidence:** `Compile/OmittedManifest.cs:32-64`, surfaced at `OccamTranscodeModels.cs:110-118` (`OccamTranscodeOmittedInfo`) inside `compile.omitted`, only present when `Truncated=true` (`OccamTranscodeResponseBuilder.BuildCompileInfo`, `OccamTranscodeModels.cs:300-333`). Derives `region` (`tail`/`middle`/`unchosen`) from the **strategy name**, not by re-parsing the in-band SNIP markers — explicitly justified in the doc comment (`OmittedManifest.cs:26-29`) because a later `PreserveDefinitionalAnchor` re-truncation could invalidate stale markers if they were the source of truth. This is the correct fail-safe direction (derive from authoritative state, not scrape rendered text) — verified sound.
`SectionsOmitted` is a coarse proxy: counts `##`/`###` heading lines before/after (`OmittedManifest.cs:66-86`) — does not distinguish "a whole section vanished" from "a section's body shrank but the heading survived"; a heading-count diff of 0 does not imply nothing was dropped from within surviving sections. Callers should not treat `sectionsOmitted:0` as "content-complete" — and none of the current downstream consumers (`OccamTranscodeTool.cs`) do; it's advisory-only.
Nested under `Structured` (`OccamTranscodeStructuredDroppedInfo`, `:121-133`) is the per-bucket drop count from `ResponseBudgetPlanner.TrimStructured`'s `ResponseBudgetDropped` (CAP-301) — correctly wired end to end (`OccamTranscodeModels.cs:318-327`).

### CAP-311 — `MaterializationAssessment` / `focus`+`completeness` semantic verdict fields
**Status:** LIVE. **Evidence:** `Knowledge/MaterializationAssessment.cs:21-69` (`Evaluate`), consumed via `Semantics.SemanticOutcomeMapper.MapFocus`/`MapCompleteness` at `OccamTranscodeTool.cs:251-255` into the response's top-level `focus`/`completeness` fields (`OccamTranscodeModels.cs:279-282`). Three completeness states: `Complete`/`Partial`/`Incomplete` (`MaterializationAssessment.cs:5-10`). `Incomplete` fires specifically when the section the focus query resolved to (`SectionRanker.Select`) exists, but the **minimum answer unit** for that section (`AnswerUnitSelector.Select`, CAP-313) did not survive the budget cut (`ContainsUnit` check, `:47-56, 65-68`) — this is a genuine, non-trivial honesty signal: it distinguishes "we found the right section but truncated its core answer" (`focus_body_truncated`) from "the whole document doesn't mention this" (`source_missing`).
**Correctness note:** `ContainsUnit` (`:65-68`) does an exact-substring `Contains` per non-heading block of the answer unit against the *final* compiled markdown — any BM25/rewrite-induced reflow inside `FitMarkdown` (which rewrites list-line text via `FilterListLinesByFocus`, `FitMarkdown.cs:423-451`) could cause a false `Incomplete` even when the *semantic* content survived in reworded form. This is a conservative fail-closed bias (errs toward reporting incomplete rather than falsely claiming complete) — consistent with the project's stated honesty-first design (`AGENTS.md` "ok:false means unknown"), so this is an intentional trade-off, not a bug, but worth naming since it can produce a `completeness_partial`/`incomplete` warning (`OccamTranscodeTool.cs:432-441`) even on a fully-answered focus query if `fit_markdown` reworded the surviving text.

### CAP-312 — `SectionIndex` / `SectionRanker`: deterministic local focus-section resolver
**Status:** LIVE. **Evidence:** `Compile/SectionIndex.cs:42-215` (heading tree with parent-stack nesting, explicit `{#anchor}` support, duplicate-anchor disambiguation via `-2`/`-3` suffixes at `:119-124`) and `SectionRanker.Select` (`:220-323`, scoring: exact-fragment 10000 → exact-anchor 4000 → exact-heading 2500 → heading-term-hits×350 → body-term-hits×45 → definitional-answer bonus 900 → index-page penalty −3000). Used by both `TokenBudget.TruncateFocusCentered` (CAP-309) and `MaterializationAssessmentEvaluator.Evaluate` (CAP-311) — i.e. the **same** section-resolution logic backs both what gets kept and what gets reported as focus status, so the two signals cannot disagree with each other by construction (single source of truth for "which section answers this query").
`IsIndexLike` detection (`SectionIndex.cs:164-168`): triggers on heading text containing "table of contents"/"index" **or** link-density ≥ 0.35 — this second condition is a real structural signal (not a keyword list) and is reused correctly.

### CAP-313 — `AnswerUnitSelector`: minimum bounded heading+body unit
**Status:** LIVE. **Evidence:** `Compile/AnswerUnit.cs:8-43`. Builds `{heading, first prose paragraph, nearest structured block+its label}` — a compact "just enough to answer" unit used by both `TokenBudget.TruncateSectionFocusAware` (protects this unit first, then greedily adds more blocks that still fit, `TokenBudget.cs:316-341`) and `MaterializationAssessmentEvaluator` (checks it survived, CAP-311). `EvidenceKind` classification (`prose`/`code`/`table`/`list`) is structural (first-line prefix sniff, `IsStructured`/`StructuredKind`, `:51-66`) — correctly cheap and deterministic.

### CAP-314 — `MaterializationKey`: deterministic content-addressed materialization identity
**Status:** LIVE. **Evidence:** `Compile/MaterializationKey.cs:21-59`, computed and returned as `materializationKey` on every success response (`OccamTranscodeTool.cs:274-281, 356`). SHA-256 over a canonical newline-delimited descriptor covering `url + backend + max_tokens + fit_markdown + focus_query + content_selectors[] + playbook_policy/id/version + semantic_chunking + json_blocks/tables/feed + translate_to + rank_blocks + tag_trust + capture_screenshot`. Schema-versioned (`mat-v1`, `:16`) for forward migration.
**Divergence vs. cache key (CAP-330):** `TranscodeCacheKey.Compute` (`Caching/TranscodeCacheKey.cs:19-48`) is a **structurally near-identical but independently-maintained** canonicalization — same field set minus `playbook_id/version`, `rank_blocks`, `tag_trust`, plus its own URL-normalization helper (`NormalizeUrl`, re-implemented, not shared with `MaterializationKey`). Two hand-written canonical-string builders covering overlapping-but-not-identical option sets is a real duplication/drift risk: a new transcode option that affects output must be remembered to be added to **both** builders, and nothing enforces that (confirmed: `rank_blocks`/`tag_trust` are in `MaterializationKey` but **absent** from `TranscodeCacheKey` — meaning two calls that differ only in `rank_blocks` will collide on the same cache entry key while producing genuinely different `blocks[].salience` output... except cache only stores/replays the full JSON envelope (CAP-330), so a cache hit would replay stale `rank_blocks` output for a request that changed only that flag. **This is a real cache-key bug tracked here as CAP-315.**

### CAP-315 — BUG: `TranscodeCacheKey` omits `rank_blocks`/`tag_trust`/`emit_capsule` — cache-poisoning risk for block annotations
**Status:** LIVE BUG (low severity, requires `cache_ttl_s` opt-in). **Evidence:** compare `TranscodeCacheKey.Compute` (`Caching/TranscodeCacheKey.cs:19-48`, fields: url/backend/max_tokens/fit_markdown/focus_query/content_selectors/playbook_policy/semantic_chunking/capture_screenshot/json_blocks/json_tables/json_feed/translate_to) against the actual request-affecting parameters read directly by `OccamTranscodeTool.Transcode` (`OccamTranscodeTool.cs:65-67`: `rank_blocks`, `tag_trust`, `delta_only`) and `:64` (`emit_capsule`). None of `rank_blocks`, `tag_trust`, `emit_capsule` participate in the cache key. Concretely: call A with `cache_ttl_s=60, json_blocks=true, focus_query="x"` populates the cache with un-annotated blocks; call B, seconds later, with identical params plus `rank_blocks=true` will **hit the same cache entry** (`TranscodeCacheEligibility.IsCacheable` at `TranscodeCacheEligibility.cs:13-41` does not special-case this either) and silently return blocks **without** the `salience` field the caller explicitly asked for, with no error or warning. `emit_capsule` is lower-impact (capsule presence/absence, not correctness) but same mechanism.
**Confirmed not mitigated elsewhere:** `TranscodeCacheEligibility.IsCacheable` only excludes `session_profile`, `if_none_match`, `diff_against`/`prefer_llms_txt` (via the tool-level `cacheable` composite check, `OccamTranscodeTool.cs:119-121`) — `rank_blocks`/`tag_trust`/`emit_capsule` are not in that exclusion list either.

## 3. Structured output surfaces (json_blocks / json_tables / json_feed / chunks)

### CAP-316 — `json_blocks`: DOM-derived structured blocks with real CSS `source_selector`
**Status:** LIVE, OPT-IN. **Evidence (worker):** `workers/shared/lib/dom-blocks.mjs:65-131` (`collectBlocks`/`pushBlock`) walks the same `mediaRoot` DOM used for media-ref extraction, capped at `DEFAULT_MAX_BLOCKS=400` blocks / `MAX_TEXT_LENGTH=8000` chars/block / `MAX_LINKS_PER_BLOCK=32` (`:13-15`). Selector is **document-absolute and round-trip-verified** (`verify()` at `:218-224` does a real `querySelector` round-trip) when the DOM is connected; falls back to wrapper-relative when detached (Readability re-serialization case, `:9-11, 158-167`) — this is a genuinely honest claim (the tool description at `OccamTranscodeTool.cs:57` says exactly this and the code backs it).
**Host-side reconciliation:** `BlockReconciler.SurvivingBlocks` (`Compile/BlockReconciler.cs:24-63`) re-filters worker blocks against the *post-compile* markdown so `blocks[]`/`blockMerkleRoot`/`contentHash` never describe pruned-away content (SI-02 integrity, doc comment `:8-17`) — verified this is called unconditionally in the live path (`TranscodePipeline.cs:326`) whenever any budget/selector/fit step could have changed the markdown, not just when `json_blocks=true` (the reconcile itself is cheap/no-op when blocks is null).
**Fallback derivation risk (acceptable):** `TryDeriveSurvivingText` (`BlockReconciler.cs:194-229`) keeps a **partial** block when ≥50% of its non-empty lines still literally appear in the compiled text (line-level containment) — a real design choice to tolerate `FitMarkdown`'s per-line list filtering (CAP-308) without discarding an otherwise-valid block entirely; the 50%-of-lines threshold is a hardcoded literal with no test-documented rationale beyond the inline comment.

### CAP-317 — `rank_blocks`/`tag_trust`: post-hoc block annotation, requires `json_blocks=true`
**Status:** LIVE, OPT-IN. **Evidence:** `BlockSalience.Annotate` (`Compile/BlockSalience.cs:15-46`, normalized BM25 score 0–1 via `ClaimBlockRanker.Rank`) and `BlockTrust.Annotate` (`Compile/BlockTrust.cs:23-38`, two heuristic channels: `suspicious` via a prompt-injection-shape regex `DirectiveRegex` at `:42-49`, `boilerplate` via a non-content-region-selector regex `BoilerplateRegionRegex` at `:53-56`). Both mutate `WorkerExtractBlockInfo` **in place** post-reconcile (`OccamTranscodeTool.cs:260-271`), gated correctly on `unchanged != true && !deltaPrimary` so conditional/delta responses never carry stale annotations. `rank_blocks` silently no-ops (no warning) if `focus_query` is absent (`OccamTranscodeTool.cs:260`: `&& !string.IsNullOrWhiteSpace(focus_query)`) despite the tool description claiming it "requires… focus_query" — the requirement is enforced by silent skip, not a validation error; an agent that forgets `focus_query` gets blocks back with no `salience` field and no warning telling them why.
**Prompt-injection detector scope:** `DirectiveRegex` (`BlockTrust.cs:42-49`) is English-only (`"ignore previous instructions"`, `"you are now an assistant"`, `"system:"`, `"as an AI"`) — a non-English injection attempt (e.g. Russian "игнорируй предыдущие инструкции") would not be flagged `suspicious`. Documented as heuristic-not-guarantee in the doc comment (`:14-16`), so this is a known/acknowledged limitation, not a silent one — but worth flagging given the security-adjacent nature of the feature.

### CAP-318 — `json_tables`: physical rows + optional reconstructed semantic `records[]`
**Status:** LIVE, OPT-IN. **Evidence:** described at `OccamTranscodeTool.cs:58`; mapped host-side via `WorkerKnowledgeMapper.MapTable`/`MapRecord` (`Knowledge/WorkerKnowledgeMapper.cs:36-61`) into `KnowledgeTable.SemanticRows` — this IR is then consumed by `TableSemanticMaterializer.Materialize` (`Knowledge/TableSemanticMaterializer.cs:12-21`) for the **compat/bench path only** (see CAP-322 — the live transcode path does not call `TableSemanticMaterializer` directly; it goes through the general `MaterializationPlanner.Plan(request, bundle)` overload instead, `TranscodePipeline.cs:271`). `records[]` provenance (`KnowledgeRowProvenance`: `SourceSelector`, `RowIndexes[]`, `TableSelector`) ties a reconstructed semantic object back to its physical DOM rows without ever mutating the markdown table — a genuinely lossless design (physical rows stay one-per-`<tr>`; semantic reconstruction rides alongside).
**Table budget cost model gap:** `ResponseBudgetPlanner.EstimateTable` (CAP-302) counts `Records[]` sub-field costs **in addition to** `Headers`/`Rows` costs (`ResponseBudgetPlanner.cs:332-341`) — meaning a table with `records` populated costs roughly double (physical rows + semantic reconstruction) against the same budget pool, with no way to request "records only, skip physical rows" to save tokens when the caller only wants the semantic view.

### CAP-319 — `json_feed`: RSS/Atom/JSON-Feed parse replaces article extraction entirely
**Status:** LIVE, OPT-IN. **Evidence:** `workers/shared/lib/feed-items.mjs:68-157` (`collectFeedItems`/`collectJsonFeed`), capped at `DEFAULT_MAX_ITEMS=200` items / `MAX_SUMMARY_LENGTH=4000` chars/summary (`:16-17`). Produces three parallel summary representations per item (`summaryHtml`/`summaryText`/`summaryMarkdown`, `formatSummaryFields`, `:165-190`) via a **hand-rolled regex HTML→text/markdown converter** (`htmlToPlainText`/`htmlToMarkdown`, `:305-345`) rather than the Turndown/Readability pipeline used for normal pages — a deliberate perf trade-off documented in the file header (`:13`: "no per-item JSDOM/Turndown") but means feed-embedded HTML gets materially different (less robust) markdown conversion than a page fetched directly — e.g. no table/nested-list handling in `htmlToMarkdown`, only p/a/br/em/strong/li.
`ResponseBudgetPlanner.EstimateFeedItem` (`ResponseBudgetPlanner.cs:376-382`) sums the cost of **all four** summary fields (`summary`+`summaryHtml`+`summaryText`+`summaryMarkdown` — note `formatSummaryFields` always populates a `summary` compat alias too, `feed-items.mjs:165-190`) even though they largely duplicate content — a feed item's token cost against the shared budget is ~3-4x its actual unique information content, which can cause `TrimFeed` (`ResponseBudgetPlanner.cs:418-458`) to drop items earlier than a caller reading only `summaryText` would expect.

### CAP-320 — `semantic_chunking` (`chunks[]`): naive fixed-size line-accumulation, not semantic
**Status:** LIVE, OPT-IN. **Evidence:** `workers/shared/plugins/chunking.mjs:10-66` (`chunkMarkdown`). Despite the MCP parameter name "semantic_chunking" and plugin name `semantic_chunking` (`:69`), the algorithm is a **fixed character-length accumulator that only breaks early on a heading boundary** (`maxChunkLength` default 2000 chars via `OCCAM_CHUNK_SIZE` env var, `:11`) — it does not consider sentence boundaries, paragraph boundaries, code-fence integrity (a fenced code block can be split mid-fence across two chunks — no fence-awareness in this file, confirmed by absence of any ` ``` ` handling), or BM25/embedding relevance. The only "semantic" element is the `headers[]` breadcrumb trail attached to each chunk (tracks H1-H6 ancestry, `:36-39`, correctly handles skipped heading levels via `filter(Boolean)`, `:30/50/61`).
**Naming-vs-behavior gap:** an agent reading the parameter name/tool description (`OccamTranscodeTool.cs:55`: "Enables semantic markdown chunking") would reasonably expect chunk boundaries to respect content structure beyond headings; the actual guarantee is only "chunks respect heading breadcrumbs, not necessarily clean paragraph/sentence/code-fence edges."
**Budget interaction:** chunks are estimated via `ResponseBudgetPlanner.EstimateChunk` (`:347-356`, text + headers cost) and trimmed by the same greedy `TakePrefix` (CAP-301) — a code-fence-split chunk, if trimmed mid-list, ships broken markdown with no repair.

## 4. Cache (`cache_ttl_s`)

### CAP-321 — File-backed opt-in response cache: eligibility, key, storage
**Status:** LIVE, OPT-IN (`cache_ttl_s > 0`). **Evidence:** `Caching/TranscodeResponseCache.cs:24-136` (`FileTranscodeResponseCache`). One JSON file per key under `OCCAM_CACHE_DIR` (default `%TEMP%/occam-cache`, `ResolveDefaultDir`, `:37-43`), atomic write via temp-file + `File.Move(overwrite:true)` (`:107-121`) — durable-enough for a best-effort cache. `TryGet` fails closed on any exception (corrupt/locked file → miss, `:56-70`) and schema-version-gates entries (`CurrentSchemaVersion=1`, `:73`) so a future format change won't crash-read old entries, just miss them.
Eligibility (`TranscodeCacheEligibility.IsCacheable`, `Caching/TranscodeCacheEligibility.cs:13-41`) correctly fails closed on: non-positive TTL, `session_profile` set (never cache authenticated content), `if_none_match` set (AF-6 and cache are explicitly kept disjoint per the doc comment, `:27-28`), and private/RFC1918/localhost URLs via `PrivacyClassifier.Classify` (`:33-35`) — reuses the canonical privacy classifier rather than re-implementing host checks, good practice.
**Key composition:** see CAP-315 for the confirmed gap (missing `rank_blocks`/`tag_trust`/`emit_capsule`/`diff_against` fields — `diff_against` is excluded from caching entirely at the tool level, `OccamTranscodeTool.cs:120`, so that specific field's omission from the key literal is moot, but `rank_blocks`/`tag_trust`/`emit_capsule` are **not** excluded at the tool level and **not** in the key — the actual bug).
**Cache hit response reconstruction:** `TrySerializeCachedHit` (`OccamTranscodeTool.cs:377-397`) deserializes the stored full success envelope and re-stamps `cached:true, cacheAgeS`, fails closed (falls through to a live fetch) on any deserialize exception — safe.

### CAP-322 — Cache never expires proactively; TTL is checked only on read
**Status:** LIVE (by design, not a bug, but worth documenting the operational characteristic). **Evidence:** `FileTranscodeResponseCache.TryGet` (`TranscodeResponseCache.cs:79-93`) computes `age` and deletes-on-read if `age > ttlSeconds` (`:85-89`) — there is no background sweep/eviction; a cache directory populated with many distinct `(url, options)` keys and never re-read for those exact keys will accumulate stale files on disk indefinitely (bounded only by whatever calls happen to re-read the same key later). No `OCCAM_CACHE_DIR` size cap, no LRU, no max-entry-count enforcement anywhere in this file or its callers.

## 5. Diff / change-detection (`if_none_match`, `diff_against`, `delta_only`, `occam_watch`)

### CAP-323 — `if_none_match`: whole-body conditional via bare-hex content hash
**Status:** LIVE, OPT-IN. **Evidence:** `Compile/ContentHashToken.cs:13-32`. Bare-hex SHA-256 of the *final compiled* markdown, deliberately the same digest space as the receipt's `sha256:`-prefixed `contentHash` (`Matches` tolerates the optional prefix, `:25-31`) so a caller can round-trip `receipt.signed.contentHash` directly as next-call `if_none_match` without string manipulation — a genuinely good ergonomic detail, confirmed used this way in `OccamTranscodeTool.cs:190`.
When matched, the response omits **all** heavy sidecars (`omitHeavySidecars`, `OccamTranscodeTool.cs:285, 325-343`) — blocks/tables/chunks/feed/media/session/quality/compile all become `null`/`[]`, and even the receipt is replaced with a minimal conditional variant (`:287-296`) that omits `TokensUsed`, block leaves, capsule — this is a real token-savings feature (confirmed structurally, not just claimed): a 304-equivalent response is genuinely minimal, not just "markdown omitted with everything else intact."
**Interaction with `ResponseBudgetPlanner.Mode.Unchanged`:** `ResponseBudgetPlanner.AllocateMarkdownCap` has an explicit `Unchanged` mode (`ResponseBudgetPlanner.cs:94-104`) that allocates zero markdown floor — but tracing `BudgetOwnership.PrepareSurfaceBudget` (`BudgetOwnership.cs:41-60`) shows **no caller ever passes `mode: ResponseBudgetMode.Unchanged`** — the only call site (`TranscodePipeline.cs:249-251`) always uses the default `Full` mode. This means `unchanged:true` responses are built by **hand-omitting fields in `OccamTranscodeTool.cs`** (a separate, parallel code path) rather than by driving the `ResponseBudgetPlanner.Unchanged` mode that exists specifically for this case — **the `Unchanged`/`DeltaOnly` enum values in `ResponseBudgetMode` are effectively dead** (never selected at any call site; confirmed via grep — `ResponseBudgetMode.Unchanged`/`DeltaOnly` appear only in their own enum declaration and the `AllocateMarkdownCap` switch, never in a call argument anywhere in `src/`).

### CAP-324 — UNREACHABLE FROM LIVE CODE: `ResponseBudgetMode.Unchanged` / `ResponseBudgetMode.DeltaOnly` are exercised only by a unit test, never by the live pipeline
**Status:** DEAD (live path) / tested in isolation. **Evidence:** `grep -r "ResponseBudgetMode\.(Unchanged|DeltaOnly)"` across the whole repo matches: the enum definition (`ResponseBudgetPlanner.cs:59-67`), the `switch` arm that handles it (`:94-104`), and exactly one unit test — `benchmarks/l0-gate/ConditionalEconomyUnitTests.cs:174,177` calls `AllocateMarkdownCap(512, empty, ResponseBudgetMode.Unchanged/DeltaOnly)` directly. **Zero call sites in `src/` (the actual host runtime) ever pass either value.** `BudgetOwnership.PrepareSurfaceBudget`'s `mode` parameter defaults to `ResponseBudgetMode.Full` (`BudgetOwnership.cs:44`) and its single production caller (`TranscodePipeline.cs:249-251`) never overrides it, even on the `unchanged:true` (CAP-323) or `deltaPrimary:true` (CAP-325) branches later in the same method. The actual `unchanged`/`deltaPrimary` minimal-response behavior in production is implemented by ad-hoc field-nulling in `OccamTranscodeTool.cs` (`omitHeavySidecars` ternaries, `:325-343`), fully independent of this enum. This is a real-but-benign case of **two competing implementations of the same intent** — the enum-driven one is unit-tested but was never wired into `TranscodePipeline`; the ad-hoc one is what actually ships. Low risk today (the wired path works and is itself tested via `omitHeavySidecars`), but a maintenance trap: a future refactor might reasonably assume `ResponseBudgetMode.Unchanged` is the live mechanism controlling conditional responses, when it is not, and "the unit test passes" would not catch that the production code path never touches this enum.

### CAP-325 — `diff_against` / `delta_only`: block-level delta codec
**Status:** LIVE, OPT-IN. **Evidence:** `Tools/BlockDiff.cs:14-50`. Per-block hash = first-16-hex-chars of SHA-256 over `type+text` concatenation (`Hash`, `:17-21`) — **no length-prefix/separator between `type` and `text`** in the hash input (`$"{block.Type}{block.Text}"`, `:19`) — a block of `Type="heading", Text="1 Introduction"` and `Type="heading1", Text=" Introduction"` (contrived but structurally possible if a future worker ever emits a numbered type) would hash-collide. Currently harmless in practice since `Type` is drawn from a small closed set (`heading/paragraph/list_item/code/quote/table/figure`, `dom-blocks.mjs:36-58`) none of which is a prefix of another, but it's an unguarded assumption, not an enforced invariant.
`Compute` (`:23-49`) returns `addedBlocks` (full content for anything not in the prior hash set), `removedHashes` (prior hashes absent from current), and `blockHashes` (current full ordered list, for the *next* round-trip) — correct set-difference semantics, case-insensitive hash comparison (`OrdinalIgnoreCase`, `:27,29,45`) tolerating a caller that echoes hashes in a different case.
`delta_only` (`OccamTranscodeTool.cs:230-244`) requires **both** `diff_against` (a base) and non-empty `result.Blocks` (i.e. `json_blocks=true` produced something) — correctly fails soft with an explanatory warning rather than a hard error when either precondition is missing (`delta_only_ignored_no_base`/`delta_only_ignored_no_blocks`, `:238,242`), never silently drops the user's data.

### CAP-326 — `occam_watch`: stateful wrapper reusing the same transcode options/diff plumbing
**Status:** OPT-IN (env-gated: `OCCAM_WATCH_MCP=1`, tool doc comment `Tools/OccamWatchTool.cs:9-13`). **Evidence:** `OccamWatchTool.cs:19-60` builds a normal `OccamTranscodeOptions` via the **same** `OccamTranscodeOptionsParser.TryBuild` overload used internally by `occam_transcode` (`:42-54`), confirming there is one shared options-construction path, not a parallel reimplementation. `fit_markdown` is auto-enabled whenever `focus_query` is set (`:44`, `!string.IsNullOrWhiteSpace(focus_query)`), a UX default not exposed as an independent parameter on this tool (the caller cannot request "focus without pruning" on `occam_watch`).

### CAP-336 — Env vars actually read by this subsystem (confirmed via grep, cross-checked against `docs/configuration.md` — docs untrusted, used only as a starting point)

### CAP-337 — `OCCAM_CHUNK_SIZE` unit mismatch: chars vs. tokens
**Status:** LIVE (documented above as part of CAP-336, broken out because it's an independent, actionable finding). **Evidence:** `chunking.mjs:11` measures `currentChunkLength += line.length + 1` (JS string `.length`, i.e. UTF-16 code units ≈ characters) against a char-denominated `maxChunkLength`, while `ResponseBudgetPlanner.EstimateChunk` (`ResponseBudgetPlanner.cs:347-356`) re-measures the **same chunk text** in **tokens** via the script-aware `TokenEstimator.Estimate` (CAP-309's estimator) when deciding whether to keep it under the whole-response budget. On a non-ASCII-heavy page (Cyrillic/CJK), a chunk sized to `OCCAM_CHUNK_SIZE=2000` **characters** (worker-side) will estimate to roughly `2000 × 1.0` tokens for CJK (`TokenEstimator.CharCost`, `TokenEstimator.cs:32-39`) vs. `2000 × 0.25` tokens for ASCII — i.e. the worker produces chunks whose *token* cost varies ~4x by script even though every chunk targets the same *character* length, which then interacts unpredictably with the host's token-based `TrimStructured` (CAP-301) drop-off point per language.
